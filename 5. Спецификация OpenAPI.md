## 5.1  Объекты и ресурсы

### 5.1.1. Основные сущности

1\.     “Договор” (Contract)

| № | Свойство | Англ.  наименование | Тип данных |

## 5.3 Действия и методы API

1\.   "Авторизация" (Auth)

| № | HTTP Метод | Эндпоинт | Описание |
| ----- | :---: | ----- | ----- |
| 1 | POST | /auth/send-code  | Абонент вводит номер телефона в приложении. Система отправляет SMS с одноразовым кодом подтверждения  |
| 2 | POST | /auth/verify  | Проверить SMS-код и завершить авторизацию. В ответе возвращает Access Token, Refresh Token и идентификатор договора.  |
| 3 | POST | /auth/refresh  | Обновление Access Token. Используется для автоматического продления сессии без повторного ввода кода.  |
| 4 | POST | /auth/2fa/request  | Запросить 2FA-код для критической операции  |
| 5 | POST | /auth/2fa/verify  | Проверить 2FA-код и получить временный токен  |

Для авторизации выделен отдельный префикс /auth, так как эти эндпоинты не требуют авторизации и логически отделены от защищённого API. Метод POST выбран для передачи конфиденциальных данных в теле запроса, что соответствует лучшим практикам безопасности 

2\.    “Договор” (Contract) 

| № | HTTP Метод | Эндпоинт | Описание |
| :---: | :---: | ----- | ----- |
| 1 | GET | /api/contracts/{contractId} | Получить информацию о договоре (баланс, статус, номер телефона, остатки пакетов)  |
| 2 | GET | /api/contracts/{contractId}/balance | Получить текущий баланс. При недоступности биллинга возвращает кэшированное значение с полем cachedAt  |
| 3 | GET | /api/contracts/{contractId}/tariff | Получить текущий тариф |
| 4 | GET | /api/contracts/{contractId}/options | Получить список подключенных опций |
| 5 | PUT | /api/contracts/{contractId}/tariff | Асинхронно сменить тариф (возвращает operationId, статус отслеживается отдельно)  |
| 6 | POST | /api/contracts/{contractId}/options | Асинхронно подключить опцию (возвращает operationId, статус отслеживается отдельно)  |
| 7 | DELETE | /api/contracts/{contractId}/options/{optionId} | Асинхронно отключить опцию (возвращает operationId, статус отслеживается отдельно)  |
| 8 | GET | /api/operations/{operationId}/status  | Получить статус асинхронной операции (смена тарифа, управление опциями)  |

####  

3\.  "Тариф" (Tariff)

4\.  "Опция" (Option)

Примечание по обработке ошибки 401 Unauthorized для всех эндпоинтов:

Фронтенд не должен показывать пользователю сообщение об ошибке при получении 401 в первый раз. Он обязан:

1. Автоматически обновить Access Token через эндпоинт /auth/refresh, используя Refresh Token, сохранённый в защищенном хранилище устройства.  
2. Повторить исходный запрос с новым Access Token.

Это происходит в фоновом режиме, пользователь ничего не замечает.

Если Refresh Token также истек (редкий сценарий, например, пользователь не заходил в приложение более 30 дней), фронтенд показывает экран авторизации с сообщением: **«Ваша сессия истекла. Пожалуйста, войдите заново».**

Спецификация в формате YAML, предназначенная для генерации клиентского кода и загрузки в Swagger UI, прилагается к работе отдельным файлом (openapi.yaml), расположенным по ссылке: [openapi3\_0 Мой оператор связи.yaml](https://drive.google.com/file/d/1GpSG8H-Ci_DzbCU_U32X62Jg6wteKbMy/view?usp=sharing)

## 5.5 Описание реализованного API

API спроектирован в соответствии с принципами архитектурного стиля REST и стандартизирован с использованием спецификации OpenAPI 3.0. Все операции обмена данными между мобильным клиентом и серверной частью выполняются в формате JSON.   
API построен вокруг ключевых бизнес-сущностей предметной области: договор (Contract), тариф (Tariff), опция (Option), платёж (Payment). Каждая сущность представлена собственным URI-пространством и поддерживает стандартные HTTP-методы (GET, POST, PUT, DELETE). Это обеспечивает единообразие интерфейсов и упрощает интеграцию с клиентскими приложениями. 

Основные функциональные группы API:

* Авторизация и управление сессией (/auth/\*) \- вход по номеру телефона с подтверждением по SMS, обновление токенов, двухфакторная аутентификация для критических операций.  
* Управление договором (/api/contracts/\*) \- просмотр баланса, остатков пакетов, тарифа, опций, смена тарифа, подключение и отключение опций.  
* Справочники (/api/tariffs, /api/options) \- получение каталогов тарифов и опций с пагинацией.  
* Финансовые операции (/api/contracts/{id}/payments/recharge) \-  пополнение баланса.

В спецификации использован подход Contract-First, при котором все структуры данных описаны в блоке components/schemas и переиспользуются через механизм ссылок (\$ref). 

В целях обеспечения безопасности и упрощения настройки инфраструктуры все эндпоинты, связанные с аутентификацией, вынесены в отдельное URI-пространство /auth. Это позволяет гибко управлять политиками доступа, применять различные механизмы ограничения частоты запросов (rate limiting) и исключает необходимость проверки JWT-токенов для публичных методов. Основные бизнес-операции размещены в пространстве /api.

API реализует двухуровневую защиту:

* Первый уровень \- JWT-аутентификация (Bearer-токен), обязательная для всех защищённых эндпоинтов (с префиксом /api). Токен доступа имеет ограниченное время жизни (15 минут) и обновляется через отдельный эндпоинт /auth/refresh с использованием Refresh-токена (время жизни \- 30 дней).  
* Второй уровень \- двухфакторная аутентификация (2FA) для критических операций: смена тарифа, подключение и отключение платных опций. Для этого введены отдельные эндпоинты запроса и проверки 2FA-кода, а сами критические методы требуют передачи временного токена в заголовке X-2FA-Token. Такой подход соответствует современным требованиям к безопасности финансово-значимых операций.

Операции смены тарифа и управления опциями выполняются асинхронно ввиду возможных задержек биллинговой системы (до 30 секунд). При успешной валидации запроса сервер возвращает HTTP-статус 202 Accepted и уникальный идентификатор операции (operationId). Клиент отслеживает статус через эндпоинт GET /api/operations/{operationId}/status; по завершении операции направляется push-уведомление. Это исключает блокировку клиентского приложения и обеспечивает отказоустойчивость при интеграции с внешними системами. 

Для методов, возвращающих коллекции (каталог тарифов и опций), реализована пагинация через параметры limit и offset с значениями по умолчанию 20 и 0 соответственно. Ответы содержат массив элементов  и объект pagination с общей численностью записей, что упрощает построение навигации на клиенте.   
Все ошибки возвращаются в стандартизированной структуре ErrorResponse, содержащей код ошибки и сообщение, поясняющее ошибку. Это облегчает обработку ошибок на стороне клиента и упрощает отладку.
